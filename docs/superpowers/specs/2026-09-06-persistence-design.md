# Phase 4 Persistence Design

**Status:** Proposed

## Outcome

Phase 4 replaces the API process's in-memory todo collection with PostgreSQL.
Todos survive FastAPI and PostgreSQL container restarts, while the existing web
and iOS journey, JSON shapes, statuses, ordering, and recovery messages remain
the same.

The phase teaches one concrete SQLAlchemy mapping, explicit Alembic migrations,
request-scoped sessions, route-owned transactions, and focused tests against a
real isolated PostgreSQL database.

## Scope

This phase adds PostgreSQL 18.6 in Docker Compose, SQLAlchemy 2.x's synchronous
API, psycopg 3.3, Alembic, a todo table, and three narrow repository functions.
It updates local commands, CI, tests, and Guide 04.

It does not add edit/delete operations, users, authentication, pagination,
timestamps, soft deletion, generated clients, caching, retries, async database
libraries, generic repository/service interfaces, connection-manager classes,
or automatic schema creation. It does not change the todo screen or its state
model.

## Chosen architecture

FastAPI's blocking todo handlers become synchronous `def` routes. Each default
FastAPI app owns one SQLAlchemy `Engine` and `sessionmaker` using psycopg's
synchronous driver; an app with an injected factory uses its caller-owned
engine. FastAPI runs those handlers outside the event loop. A dependency opens
one `Session` for a request and always closes it.

POST and PATCH each own an explicit `with session.begin()` transaction. The
repository executes SQL and flushes a created row, but never commits. The
transaction exits successfully before the route returns its response model, so
`201` or `200` means the write committed. An exception rolls the transaction
back. GET executes one ordered query and the request-scoped session closes its
read transaction.

The app lifespan creates its default engine and sessionmaker without opening a
database connection. The engine uses `pool_pre_ping=True`, a three-second driver
connection timeout, and a three-second pool checkout timeout. Its sessionmaker
uses `expire_on_commit=False`, so committed response fields do not trigger
another query. The first todo operation opens a connection. The same lifespan
disposes the engine it created at shutdown. Tests inject a factory backed by
their fixture engine; the fixture, rather than the app, owns and disposes that
engine at suite end.

The exact default development URL is
`postgresql+psycopg://todo:todo@127.0.0.1:5432/todo`; `DATABASE_URL` overrides
it. No dotenv or configuration framework is added.

The persistence module defines the engine/session lifecycle. A separate todo
repository module contains the one ORM row and only these concrete operations:

```python
list_todos(session: Session) -> Sequence[TodoRow]
create_todo(session: Session, public_id: UUID, title: str) -> TodoRow
set_completed(session: Session, public_id: UUID,
              completed: bool) -> TodoRow | None
```

Routes own HTTP concerns and transactions; repository functions own SQL. PATCH
uses one `UPDATE ... RETURNING` statement, including when the requested Boolean
equals the session's current value. This atomically reports a missing UUID and
prevents a stale ORM read plus same-value assignment from returning a state that
was never written. There is no interface or service layer with one
implementation.

## Data model and ordering

Alembic revision `2026090601` creates exactly one application table:

| Column | PostgreSQL type | Rules | Purpose |
| --- | --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | primary key | Internal order and row identity |
| `public_id` | `UUID` | unique, not null | Existing public `Todo.id` |
| `title` | `TEXT` | not null; length 1–120 | Canonical title |
| `completed` | `BOOLEAN` | not null, default false | Existing completion state |

Python generates `public_id` with `uuid4()` before insertion, avoiding an
extension and preserving the UUID API contract. The internal `id` never appears
in JSON. GET orders by internal `id` ascending, and PATCH does not alter it.
This preserves the existing sequential request contract, including duplicate
titles. Identity values may have gaps after rollback, and overlapping concurrent
creates are ordered by identity allocation rather than commit time; no stronger
concurrent ordering promise is added.

There are no speculative indexes beyond the primary key and unique public ID,
and no timestamps. A named `CHECK (char_length(title) BETWEEN 1 AND 120)` is a
cheap database-native backstop; canonical trimming remains an API-boundary rule.
Alembic owns schema changes. Application startup never calls `create_all`; a
missing migration is an operator error explained by the guide.

## HTTP compatibility and failures

GET/POST/PATCH paths, request and response JSON, successful statuses, UUIDs,
duplicate behavior, completed-only PATCH semantics, `404`, OpenAPI, and CORS
remain unchanged. `/health` remains the exact database-independent liveness
contract `200 {"status":"ok"}`. It proves the API process can respond, not that
PostgreSQL is ready.

Connection/disconnect `OperationalError` and pool checkout `TimeoutError` from a
todo operation return exactly `503 {"detail":"Database unavailable."}`. A write
failure cannot return success because commit occurs before the response. The
mobile client already maps `503` to its safe unavailable/unknown-write behavior.
Other SQLAlchemy and migration errors remain `500` so defects are not mislabeled
as temporary outages.

PostgreSQL text cannot store U+0000. `TodoCreate` therefore rejects a NUL code
point with `422` before any SQL or write. This is the phase's only intentional
contract tightening. The TypeScript response guard also rejects NUL so its
runtime contract matches the server. The screen needs no change: a POST `422`
already preserves the draft and shows **Check the todo title and try again.**
ECMAScript trimming, surrogate rejection, and the 1–120-code-point rule remain.

## Local PostgreSQL and commands

`compose.yaml` defines two PostgreSQL 18.6 services with health checks:

- `db` uses user/password/database `todo`, binds `127.0.0.1:5432`, and mounts a
  named volume at PostgreSQL 18's `/var/lib/postgresql`. `compose down` keeps
  this volume; normal instructions never use `down -v`.
- profile-only `db-test` uses user/password/database `todo_test`, binds
  `127.0.0.1:5433`, and uses tmpfs at `/var/lib/postgresql`. It has no
  development volume.

The root maps `db:up` to `docker compose up -d --wait db`, `db:test:up` to
`docker compose --profile test up -d --wait db-test`, and `db:migrate` to
`uv run --directory apps/api alembic upgrade head`. The documented development
sequence is `pnpm db:up`, `pnpm db:migrate`, then `pnpm dev:api`. After one
`pnpm db:test:up`, existing `pnpm test:api` and `pnpm quality` run the API
integration tests. Tests never silently skip when PostgreSQL is absent.

## Migrations and test isolation

Alembic's command-line path reads the same `DATABASE_URL` rule as the app, with
no credential file or dotenv dependency. The initial revision has explicit
upgrade and downgrade operations, but routine startup performs only
`alembic upgrade head` through `pnpm db:migrate`.

API tests default to
`postgresql+psycopg://todo_test:todo_test@127.0.0.1:5433/todo_test`; CI sets the
exact `postgresql+psycopg://todo_test:todo_test@127.0.0.1:5432/todo_test`
through `TEST_DATABASE_URL`. Before opening a connection, migration, or cleanup,
setup requires the exact psycopg PostgreSQL driver, no URL query parameters,
database name `todo_test`, and a target different from the resolved development
URL. It then connects and verifies `current_database() = 'todo_test'`. Failure is
immediate. Tests run Alembic programmatically through that already checked
connection; Alembic's environment honors `Config.attributes["connection"]`
instead of resolving `DATABASE_URL` again. The check and upgrade run inside one
`engine.begin()` block so the migration commits before application sessions use
the schema. Only fixtures requested by database tests upgrade to head and
truncate `todos` with restarted identity; truncation runs in its own committed
`engine.begin()` block before a test opens sessions. The database tests run
serially against this shared test database. Health and model-validation tests
never connect to the database. Setup verifies the revision/table and disposes
its engine at suite end; it never drops a database, schema, or the development
volume.

Repository integration tests prove migration shape, ordered duplicates,
committed persistence across new sessions, PATCH without reordering, missing-row
behavior, rollback after an exception, and a deterministic stale-session race in
which PATCH must persist the requested Boolean. API integration tests use the
actual test PostgreSQL service for existing GET/POST/PATCH contracts and prove
data survives a new FastAPI app instance. A separate unreachable-engine test
proves todo `503` while `/health` remains `200`.

Exhaustive title-model cases move from HTTP tests into a database-free validation
test; representative canonical `201` and invalid `422` cases remain actual API
tests. Health, mobile transport, and TodoScreen component tests also remain
database-free. CI adds a PostgreSQL 18.6 service to the application job, waits
for health, sets the exact port-5432 test URL above, migrates through requested
test setup, and runs the existing quality layers. No application data or Docker
volume is shared between CI runs.

## Documentation and acceptance

Guide 04 explains the two databases, volume lifetime, migration-first startup,
transaction boundary, liveness versus database availability, focused commands,
safe test cleanup, and recovery from a stopped database. README advances to
Phase 4 and the roadmap records its approved spec only after approval.

Manual acceptance starts with a migrated empty development database. On web,
create duplicate todos and complete one; restart FastAPI and confirm the rows and
order remain. Restart the development database container without deleting its
volume and confirm the same rows remain. On iOS, refresh, reactivate a row, and
confirm web sees it. Stop PostgreSQL, verify `/health` stays healthy while todo
requests use the existing unavailable UI, restart it, and Refresh to recover.
Record actual runtimes in an initially unchecked web/iOS table.

Phase 4 completes after focused and full checks pass, manual acceptance is
recorded, Sol whole-branch review has no unresolved findings, the reviewed work
is integrated, CI passes on that integrated commit, and only then the commit is
tagged `phase-04-persistence`.

## Alternatives considered

An async SQLAlchemy/asyncpg stack would add async engines, sessions, drivers,
and test machinery without improving this tutorial-sized API. Raw psycopg SQL
would be smaller but would skip the roadmap's SQLAlchemy mapping lesson. A
generic repository plus service interface would add indirection without a
second implementation or business layer. The synchronous concrete repository
is the smallest design that teaches every Phase 4 goal.
