# Phase 6 Authentication and Authorization Design

**Status:** Design approved; local acceptance pending (2026-09-07)

## Outcome

Phase 6 gives every todo an owner and every request an identity. On web and
iOS, users sign up with a username and password, sign in to receive a session
token, and see only their own todos. Sign-out revokes the session
server-side. A signed-out client, a missing or malformed credential, an
expired session, and a revoked token all read as unauthenticated, and one
user's todo UUIDs are unresolvable — reported as missing, never forbidden —
to another user.

The phase teaches password hashing with a slow KDF, opaque server-side
sessions, Bearer credential transport, per-user SQL scoping as the
authorization boundary, platform-split secure token storage, and an explicit
signed-out/signed-in state machine that sits outside the server-state cache.

## Scope

This phase adds a `users` table, a `sessions` table, an `owner_id` column on
`todos`, signup/login/logout/session-probe endpoints, Bearer enforcement on
every todo route, a `tokenStorage` seam (`expo-secure-store` on native,
`localStorage` on web), sign-in/sign-up UI with protected navigation, and
session restore on launch.

It does not add password reset, "sign out everywhere", rate limiting or
login lockout, email identity or verification, OAuth/Apple/Google sign-in,
2FA, roles or teams, refresh-token rotation, sliding session expiry, an
expired-session janitor, timestamps, pagination, soft deletion, offline auth
queues, or automated browser/iOS E2E (the cross-platform E2E phase still owns
that). Signup does not sign in: the client performs an explicit login after a
successful signup so the credential round trip stays visible and testable.

## Chosen architecture

Credentials are username plus password. The server stores only an
argon2 (`argon2-cffi`) hash; raw passwords exist in request bodies and
transient memory and are never logged or persisted. Sessions are opaque:
login generates 32 random bytes via `secrets.token_hex(32)` (64 hex
characters — no padding or URL-encoding edge cases in headers or JSON),
returns the encoded token exactly
once, and stores only its SHA-256 hash with an absolute 30-day expiry.
Validation is one indexed lookup constrained by expiry. Logout deletes the
session row; deleting a user cascades to their sessions and their todos.
There is no refresh-token layer and no background cleanup — login
opportunistically deletes the user's expired rows.

The client presents the token as `Authorization: Bearer <token>` on every
request, set by the existing typed transport helper when a token is
available. CORS gains the `Authorization` request header; nothing else about
CORS changes. Identity state lives in a small auth owner above `TodoScreen`,
not in the TanStack Query cache: `unknown` (launching) → `signed-out` →
`signed-in(user)`. Launch with a stored token probes `GET /auth/me`; `200`
restores the user, `401` clears the store to a clean signed-out state.

## Data model and migration

Alembic revision `2026090701` owns all schema changes; application startup
never creates tables. It follows Phase 4 conventions (internal `BIGINT
GENERATED BY DEFAULT AS IDENTITY` PK, no timestamps):

| Table.column | Type | Rules | Purpose |
| --- | --- | --- | --- |
| `users.id` | `BIGINT IDENTITY` | primary key | Internal row identity |
| `users.public_id` | `UUID` | unique, not null | Public user `id`; sequential ids never leak |
| `users.username` | `TEXT` | unique, not null | Login identity |
| `users.password_hash` | `TEXT` | not null | argon2 hash, never exposed |
| `sessions.id` | `BIGINT IDENTITY` | primary key | Internal row identity |
| `sessions.token_hash` | `TEXT` | unique, not null | SHA-256 hex of the presented token |
| `sessions.user_id` | `BIGINT` | not null, FK `users(id)` cascade delete | Session owner (cascade is defense in depth; no user-deletion endpoint exists in this phase) |
| `sessions.expires_at` | `TIMESTAMPTZ` | not null | Absolute expiry |
| `todos.owner_id` | `BIGINT` | not null, FK `users(id)` cascade delete | Todo owner (user deletion, if ever added, cannot orphan or leak rows) |

Python generates `users.public_id` with `uuid4()` before insertion,
preserving the UUID API convention without an extension. `expires_at` is a
functional column (expiry enforcement), not audit metadata — there are still
no `created_at`/`updated_at` columns anywhere. Usernames are
3–32 characters from letters, digits, `_`, `-` (case-sensitive, no
whitespace possible by construction). Passwords are 8–128 code points with
no composition rules and no trimming — length over `P@ssw0rd!` games —
rejecting NUL before hashing.

The migration deletes all existing ownerless `todos` rows first, then adds
the non-null `owner_id`. Rationale: a nullable owner would permanently
weaken the invariant for tutorial convenience, and refusing to migrate on
non-empty tables turns Alembic into a babysitter. Only local development
data is affected, it is recreatable in seconds, and the guide says so
before the migrate command. There are no speculative indexes beyond primary
keys, the unique username/token-hash constraints, and the foreign keys.

## HTTP and authorization contracts

Auth responses expose exactly `{"id": <public UUID>, "username": string}`;
hashes, internal ids, and tokens-at-rest never appear in JSON.

| Operation | Request | Success | Errors |
| --- | --- | --- | --- |
| `POST /auth/signup` | `{"username", "password"}` | `201` and the user object | `422` invalid fields or duplicate username (signup necessarily reveals whether a name is taken; the vagueness guarantee below applies to login, where silent treatment would strand the client) |
| `POST /auth/login` | `{"username", "password"}` | `200` and `{"token", "expires_at", "user"}` | `401` invalid credentials (deliberately vague; no username-vs-password oracle) |
| `POST /auth/logout` | Bearer token | `204`, empty body | none — idempotent even for unknown tokens |
| `GET /auth/me` | Bearer token | `200` and the user object | `401` unauthenticated |
| `GET/POST /todos`, `PATCH/DELETE /todos/{id}` | Bearer token, existing shapes | Existing statuses, scoped to the caller | `401` unauthenticated; cross-user UUIDs read as `404`, never `403` |

A FastAPI dependency resolves the credential: missing header, wrong scheme,
malformed token, unknown hash, or expired session all collapse to exact
`401 {"detail":"Not authenticated."}` with no distinguishing detail. Every
todo statement is scoped with `WHERE owner_id = current_user` at the SQL
layer, so authorization holds even if a route forgets to check — there is no
route-only enforcement to drift. Duplicate usernames return `422` to keep the
client's single validation-copy story; no new client error category is
introduced for them.

`GET /health` stays database-independent liveness. The `503` database
behavior is unchanged. OpenAPI publishes the auth schemas and the Bearer
requirement; the todo schemas themselves do not change shape.

## Token lifecycle

The raw token is returned exactly once, in the login response, and is never
logged. At rest only the SHA-256 hex exists, so a database read alone never
yields a usable credential. Enforcement is a single query constrained by
`expires_at > now()` — no second round-trip. Absolute 30-day expiry keeps
one timestamp and zero per-request writes; there is deliberately no sliding
window. Expired sessions read exactly like absent ones. Logout deletes the
presenting row; logout with an unknown or already-revoked token still
returns `204`.

## Mobile client

`src/auth/tokenStorage.ts` exposes exactly `get/set/clear`, Promise-based,
with a native `expo-secure-store` implementation (the phase's only new
dependency) and a web `localStorage` implementation behind the same
interface. The guide documents the split frankly: hardware-backed on
native, XSS-readable on web.

The transport helper takes an optional token and sets the Bearer header;
`401` maps to a new `auth-required` error kind with safe copy, and any
`401` also returns the UI to the signed-out state — a revoked token must
never strand the user on a locked todo list. Sign-in and sign-up share one
screen with a mode toggle (one open form at a time, mirroring the
edit/confirm pattern); signup success leads to explicit login. Sign-out
clears the store, clears the query cache, and returns to signed-out. The
todo UI itself is otherwise untouched: filters, optimistic completion,
locks, and copies from Phase 5 carry over, now operating on one user's
rows. TodoScreen tests keep the fresh-QueryClient-per-case pattern with an
in-memory storage double — never the real SecureStore or localStorage in
tests — and fake timers only where timing is asserted.

## Deterministic testing

DB-free unit tests cover the username/password validation matrix,
NUL/surrogate hygiene, and hash verify round-trips. Repository integration
tests reuse the guarded `todo_test` fixtures for user create/duplicate
rejection, session create/lookup/expiry boundary, owner ordering, and
cascade deletes (repository level, via direct deletes — no user-deletion
endpoint exists to exercise them over HTTP). API integration tests prove the full
signup→login→CRUD→logout cycle, the cross-user isolation matrix (B's UUIDs
are `404` for A on GET/PATCH/DELETE), exact `401` for every unauthenticated
shape, `422` shapes, OpenAPI publication, and the `Authorization` CORS
header. Client tests prove header presence/absence and the `401` mapping;
component tests prove unknown/signed-out/signed-in states, restore via
`/me`, the signup→login round trip, mid-session `401` drop with store
clear, sign-out cache clear, and single-submit gating.

## Documentation and acceptance

Guide 06 explains password hashing, opaque sessions, the Bearer boundary,
per-user SQL scoping, the storage split and its web tradeoff, the auth
state machine, and why reset flows, lockout, refresh rotation, and OAuth
are absent. README advances to Phase 6 and the roadmap records this spec
as approved only after approval.

Manual acceptance uses two users (for example `alice` and `bob`) with
recognizable `Phase 6` todo titles. On web, sign up both, confirm each
sees an empty list, create rows as each, and confirm cross-user UUIDs are
unreachable. Restart FastAPI and confirm sessions still validate
(server-side sessions need no app memory). Restart the database container
without deleting its volume and confirm sessions and rows survive. On iOS,
repeat sign-in and isolation, then sign out and confirm the store is
cleared. Record actual web and reference-Simulator runtimes.

Phase 6 completes after focused and full checks pass, both-target
acceptance is recorded, Sol whole-branch review has no unresolved
findings, the reviewed work is integrated, CI passes on that exact
commit, and only then the commit is tagged `phase-06-auth`.

## Alternatives considered

Stateless JWT access tokens would remove the per-request lookup but add
short expiries, a refresh-token layer, and awkward pre-expiry revocation —
cryptography ceremony beyond this phase's learning goal, with the lookup
cost irrelevant at this scale. HttpOnly cookies would improve the web XSS
story but have no native cookie jar, force `SameSite=None; Secure` (HTTPS
in dev) for cross-origin work, and demand anti-CSRF tokens on mutations —
a second mechanism smuggled into the phase. Email identity would drag in
normalization and verification flows with no way to perform them locally.
Memory-only token storage would sign users out on every reload and make
restart acceptance undemonstrable. Sliding expiry would cost a write per
request for no tutorial benefit.
